# ServiceMonitor – система мониторинга доступности сервисов

## Назначение

ServiceMonitor – приложение для проверки доступности веб-сервисов
(YouTube, Telegram, Яндекс и др.) и мониторинга собственных сайтов.
Консольная версия приложения (ПР3) дополнена веб-интерфейсом
на Django (ПР5).

Приложение позволяет:

* просматривать список сервисов в браузере;
* просматривать информацию о конкретном сервисе;
* просматривать список групп сервисов;
* просматривать сервисы выбранной группы и статистику проверок;
* проверять доступность сервиса с выводом статуса и истории;
* находить сервисы по названию;
* добавлять, изменять и удалять сервисы;
* проверять все сервисы одновременно с обновлением статусов
  в реальном времени и плашкой «обновлено»;
* хранить данные между запусками приложения.

## Используемые технологии

* Python 3;
* Django 5.2 – веб-фреймворк;
* HTML – разметка веб-страниц;
* CSS и Bootstrap 5.3 – оформление страниц;
* urllib – HTTP-запросы (проверка доступности);
* JSON – хранение данных;
* pytest – автоматизированные тесты;
* flake8 – проверка качества кода.

## Целевая аудитория

Пользователи, которым нужно знать доступность сервисов
(YouTube, Discord, Telegram и др.), и веб-мастера,
которым нужен мониторинг собственных сайтов.

## Предметная область

Основными объектами предметной области являются:

* группа сервисов;
* сервис;
* результат проверки.

Группа объединяет сервисы по назначению. Каждый сервис имеет URL
для проверки и принадлежит одной группе. Проверка сервиса создаёт
результат проверки: доступность, код HTTP-ответа и время пинга.
Один сервис может иметь много результатов – из них складывается
история проверок.

## Основные сущности

### Group – группа сервисов

Объект `Group` представляет группу, к которой принадлежат сервисы.

Основные атрибуты:

* `name` – название группы;
* `description` – описание группы;
* `services` – список сервисов группы.

Основные методы:

* `add_service()` – добавление сервиса в группу;
* `remove_service()` – удаление сервиса из группы;
* `__str__()` – строковое представление группы.

### Service – сервис

Объект `Service` представляет отслеживаемый веб-сервис.

Основные атрибуты:

* `name` – название сервиса;
* `url` – URL-адрес для проверки;
* `description` – описание сервиса;
* `group` – группа сервиса;
* `checks` – история результатов проверок.

Основные методы:

* `check()` – проверка доступности (таймаут 10 с)
  и запись результата;
* `record_result()` – сохранение результата в историю;
* `last_check()` – последний результат проверки;
* `get_status_text()` – текстовый статус сервиса;
* `to_dict()`, `from_dict()` – преобразование данных JSON;
* `__str__()` – строковое представление сервиса.

### CheckResult – результат проверки

Объект `CheckResult` представляет результат одного пинга сервиса.

Основные атрибуты:

* `service` – сервис, который проверялся;
* `available` – доступен ли сервис;
* `code` – код HTTP-ответа;
* `checked_at` – время проверки.

Основные методы:

* `__str__()` – строковое представление результата.

## Страницы веб-интерфейса

* `/` – главная страница: описание приложения, счётчики данных
  и навигация (view-функция `index()`);
* `/services/` – список сервисов из `data/*.json` с сортировкой
  по названию, статусами-бейджами, кнопками проверки и кнопками
  CRUD (view-функция `services()`);
* `/services/check/` – проверка всех сервисов одним действием
  без JavaScript, затем возврат к списку
  (view-функция `check_all()`);
* `/services/new/` – форма добавления нового сервиса
  (view-функция `service_create()`);
* `/services/<str:slug>/check/` – проверка одного сервиса:
  для JavaScript возвращается JSON со статусом, без него –
  редирект к списку или к карточке (`?next=detail`)
  (view-функция `service_check()`);
* `/services/<str:slug>/edit/` – форма изменения данных сервиса
  (view-функция `service_edit()`);
* `/services/<str:slug>/delete/` – подтверждение и удаление
  сервиса (view-функция `service_delete()`);
* `/services/<str:slug>/` – страница сервиса: карточка
  с данными, проверка доступности, история проверок и кнопки
  CRUD (view-функция `service_detail()`);
* `/groups/` – список групп сервисов из `data/groups.json`
  (view-функция `groups()`);
* `/groups/<str:group_slug>/` – страница группы: описание,
  сервисы группы и статистика проверок
  (view-функция `group_detail()`).

Страницы отдаются с заголовком `Cache-Control: no-store`:
браузер не показывает устаревшую копию, данные перечитываются
при каждом открытии. Кнопки «Проверить» и «Проверить все
сервисы» отправляют запросы всем адресам одновременно: по мере
ответов статус обновляется на месте, рядом с сервисом
появляется плашка «обновлено» и исчезает через две секунды.
Без JavaScript работает запасной вариант с редиректом
на обновлённый список.

Идентификатор сервиса в URL совпадает с именем его JSON-файла
без расширения (`/services/youtube/`), идентификатор группы
получается из названия нижним регистром с подчёркиваниями
(`/groups/соцсети_и_мессенджеры/`). Если сервис или группа
с указанным идентификатором не найдены, страница возвращает
код статуса 404.

Для адресов, которым не нашлось ни одного маршрута, работает
собственная страница ошибки: в корневом `servicemonitor/urls.py`
объявлен обработчик `handler404 = "homepage.views.page_not_found"`,
а сама view-функция `page_not_found()` собирает страницу общим
каркасом `page()` и возвращает ответ с кодом 404. Обработчик
действует для всех приложений сразу и виден при `DEBUG = False`
(при отладке Django показывает техническую страницу). В файле
`settings.py` для работы при выключенной отладке заполнен
`ALLOWED_HOSTS`, а параметры локализации заданы как
`LANGUAGE_CODE = "ru-RU"` и `TIME_ZONE = "Europe/Moscow"`.

## Основные операции

### Используется в веб-интерфейсе (ПР5)

* просмотр списка сервисов;
* просмотр информации о сервисе;
* просмотр списка групп;
* просмотр информации о группе и её сервисах;
* добавление, изменение и удаление сервисов;
* проверка всех сервисов одной кнопкой в реальном времени;
* проверка отдельного сервиса кнопкой из списка или со
  страницы самого сервиса;
* проверка доступности сервиса с историей проверок;
* статистика проверок по группе.

### Отложено до следующих работ

Эти операции реализованы в ПР3 и работают в консольной версии.
В веб-интерфейсе они появятся позже:

* поиск сервиса по названию;
* сортировка и выборка сервисов по запросу.

## Хранение данных

Данные приложения хранятся в JSON-файлах:

* `data/groups.json` – группы сервисов;
* `data/<имя_сервиса>.json` – по одному файлу на каждый сервис.

При загрузке данные из JSON преобразуются в объекты `Group`
и `Service`. При сохранении объекты преобразуются в данные JSON.
Для связи сервиса с группой в его файле используется название
группы `group`.

Имя JSON-файла всегда совпадает с именем сервиса в нижнем
регистре с подчёркиваниями вместо пробелов — по нему строится
идентификатор сервиса в URL.

Группа «Тестовые сервисы» содержит сайты с нестандартным
поведением для наблюдения за реакцией мониторинга:

* `dns-отказ` – домен `.invalid` (IANA): отказ за 0.02 с;
* `ssl-ошибка` – просроченный сертификат: TLS-отказ за 0.5 с;
* `http_503` – httpbin.org отвечает 503 сразу, без таймаута;
* `медленный_ответ` – ответ приходит через ~5–6 секунд;
* `чёрная_дыра` – TEST-NET-1 (RFC 5737): висит ровно
  до таймаута 10 секунд;
* `google_generate_204` – спец-эндпоинт Google для проверки
  соединения: отвечает 204 за 0.2 с.

## Назначение модулей

### `main.py`

Консольная версия приложения (сохранена с ПР3).
Отвечает за:

* запуск консольного приложения;
* отображение меню;
* получение данных от пользователя;
* организацию пользовательских сценариев.

### `servicemonitor/`

Пакет настроек Django-проекта:

* `settings.py` – настройки проекта (подключены приложения
  `homepage`, `services`, `groups`);
* `urls.py` – маршрутизация верхнего уровня;
* `asgi.py`, `wsgi.py` – точки взаимодействия с сервером.

### `homepage/`

Django-приложение, отвечающее за главную страницу:

* `views.py` – функция `page()` (общий HTML-каркас),
  view-функция `index()` и обработчик `page_not_found()`
  (собственная страница 404);
* `urls.py` – маршрут главной страницы.

Функция `page()` размещена здесь, потому что главная страница
задаёт общий вид всех остальных страниц – она точка входа
в проект. Остальные приложения импортируют её.

### `services/`

Django-приложение, отвечающее за сервисы:

* `views.py` – view-функции `services()` и `service_detail()`,
  CRUD-функции (`service_create()`, `service_edit()`,
  `service_delete()`), проверки (`check_all()`,
  `service_check()`), сборка HTML-форм, JSON-ответы
  для JavaScript и плашка «обновлено»;
* `urls.py` – маршруты приложения;
* `models.py` – Django-модели (заполняется в следующих работах).

### `groups/`

Django-приложение, отвечающее за группы сервисов:

* `views.py` – view-функции `groups()` и `group_detail()`;
* `urls.py` – маршруты приложения;
* `models.py` – Django-модели (заполняется в следующих работах).

### `group.py`, `service.py`, `check_result.py`, `monitor.py`

Классы предметной области (пакет ПР3):

* `group.py` – класс `Group` и связи с сервисами;
* `service.py` – класс `Service`, проверка доступности;
* `check_result.py` – класс `CheckResult` – результат проверки;
* `monitor.py` – класс `Monitor` – система, целостность связей
  и параллельная проверка всех сервисов с выводом результатов
  по мере поступления ответов.

### `checker.py`

Чистые функции-запросы над коллекциями:

* `service_slug()`, `group_slug()` – идентификаторы для URL;
* `find_service_by_slug()`, `find_group_by_slug()` – поиск
  объектов по идентификатору; используется веб-страницами
  сервиса и группы;
* `search_services()`, `sort_services()` – поиск и сортировка;
* `collect_results()`, `count_available()`,
  `percent_available()` – сбор и подсчёт результатов проверок
  (используется страницей группы).

### `storage.py`

Отвечает за загрузку и сохранение данных. Выполняет
преобразование:

* JSON → объекты Python;
* объекты Python → JSON.

### `utils.py`

Содержит вспомогательные функции консольного ввода:

* `input_int()` – безопасный ввод целого числа;
* `input_str()` – безопасный ввод непустой строки.

### `tests/`

Содержит автоматизированные тесты проекта.

## Запуск приложения

Установка зависимостей:

```text
pip install -r requirements.txt
```

Веб-версия (Django):

```text
python manage.py migrate
python manage.py runserver
```

После запуска открыть в браузере адрес:

```text
http://127.0.0.1:8000/
```

Консольная версия (сохранена):

```text
python main.py
```

## Текущее состояние и план развития

Реализовано (ПР5):

* Django-проект и три Django-приложения (`homepage`, `services`,
  `groups`);
* маршрутизация URL двух уровней;
* view-функции и страницы;
* отображение данных предметной области (сервисы и группы);
* проверка доступности сервиса через логику ПР3;
* CRUD-операции над сервисами (HTML-формы с CSRF-защитой);

  `ThreadPoolExecutor`, в браузере через JavaScript
  с плашкой «обновлено»;
* навигация между страницами;
* оформление Bootstrap 5.3.

Планируется:

* перенос сущностей `Group`, `Service` и `CheckResult` в Django ORM;
* подключение базы данных;
* переход на шаблоны (`templates/`) и отказ от функции `page()`;
* Django-формы (`forms.py`) вместо ручной сборки HTML;
* использование отложенной логики ПР3 (поиск, сортировка);
* разработка API;
* контейнеризация приложения;
* настройка CI/CD.
