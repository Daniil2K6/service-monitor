# ServiceMonitor – система мониторинга доступности сервисов

## Назначение

ServiceMonitor – приложение для проверки доступности веб-сервисов
(YouTube, Telegram, Яндекс и др.) и мониторинга собственных сайтов.
Консольная версия приложения (ПР3) дополнена веб-интерфейсом
на Django (ПР5), который переведён на систему шаблонов (ПР6).

Приложение позволяет:

* просматривать список сервисов в браузере;
* просматривать информацию о конкретном сервисе;
* просматривать список групп сервисов;
* просматривать сервисы выбранной группы и статистику проверок;
* проверять доступность сервиса с выводом статуса и истории;
* находить сервисы по названию;
* добавлять, изменять и удалять сервисы;
* проверять все сервисы одновременно с обновлением статусов
  в реальном времени и плашкой «обновлено»;
* хранить данные между запусками приложения.

## Используемые технологии

* Python 3;
* Django 5.2 – веб-фреймворк;
* Django Template Language (DTL) – шаблоны страниц;
* HTML – разметка веб-страниц;
* CSS и Bootstrap 5.3 – оформление страниц;
* JavaScript – проверка сервисов в реальном времени
  и текущий год в подвале;
* статические файлы Django (CSS, изображение, JavaScript);
* urllib – HTTP-запросы (проверка доступности);
* SQL – язык структурированных запросов к базе данных;
* SQLite и модуль `sqlite3` – реляционное хранилище (ПР7);
* JSON – исходные данные, перенесённые в базу;
* pytest – автоматизированные тесты;
* flake8 – проверка качества кода.

## Целевая аудитория

Пользователи, которым нужно знать доступность сервисов
(YouTube, Discord, Telegram и др.), и веб-мастера,
которым нужен мониторинг собственных сайтов.

## Предметная область

Основными объектами предметной области являются:

* группа сервисов;
* сервис;
* результат проверки.

Группа объединяет сервисы по назначению. Каждый сервис имеет URL
для проверки и принадлежит одной группе. Проверка сервиса создаёт
результат проверки: доступность, код HTTP-ответа и время пинга.
Один сервис может иметь много результатов – из них складывается
история проверок.

## Основные сущности

### Group – группа сервисов

Объект `Group` представляет группу, к которой принадлежат сервисы.

Основные атрибуты:

* `name` – название группы;
* `description` – описание группы;
* `services` – список сервисов группы.

Основные методы:

* `add_service()` – добавление сервиса в группу;
* `remove_service()` – удаление сервиса из группы;
* `__str__()` – строковое представление группы.

### Service – сервис

Объект `Service` представляет отслеживаемый веб-сервис.

Основные атрибуты:

* `name` – название сервиса;
* `url` – URL-адрес для проверки;
* `description` – описание сервиса;
* `group` – группа сервиса;
* `checks` – история результатов проверок.

Основные методы:

* `check()` – проверка доступности (таймаут 10 с)
  и запись результата;
* `record_result()` – сохранение результата в историю;
* `last_check()` – последний результат проверки;
* `get_status_text()` – текстовый статус сервиса;
* `to_dict()`, `from_dict()` – преобразование данных JSON;
* `__str__()` – строковое представление сервиса.

### CheckResult – результат проверки

Объект `CheckResult` представляет результат одного пинга сервиса.

Основные атрибуты:

* `service` – сервис, который проверялся;
* `available` – доступен ли сервис;
* `code` – код HTTP-ответа;
* `checked_at` – время проверки.

Основные методы:

* `__str__()` – строковое представление результата.

## Страницы веб-интерфейса

* `/` – главная страница: описание приложения и счётчики
  сервисов, групп и проверок из базы данных
  (view-функция `index()`);
* `/services/` – список сервисов из базы данных: запрос с
  соединением таблиц `services` и `groups` (JOIN), статусами
  по последней проверке, кнопками проверки и CRUD
  (view-функция `services()`);
* `/services/search/` – поиск сервисов по части названия и по
  группе: параметры передаются в SQL отдельно
  (view-функция `service_search()`);
* `/services/statistics/` – статистика проверок: агрегатные
  запросы, группировка (GROUP BY) и фильтрация групп (HAVING)
  (view-функция `service_statistics()`);
* `/services/checks/` – история проверок: соединение таблиц
  `checks`, `services` и `groups`, фильтр по статусу
  (view-функция `service_checks()`);
* `/services/check/` – проверка всех сервисов одним действием
  без JavaScript с записью результатов в базу данных, затем
  возврат к списку (view-функция `check_all()`);
* `/services/new/` – форма добавления нового сервиса
  (view-функция `service_create()`);
* `/services/<str:slug>/check/` – проверка одного сервиса:
  для JavaScript возвращается JSON со статусом, без него –
  редирект к списку или к карточке (`?next=detail`)
  (view-функция `service_check()`);
* `/services/<str:slug>/edit/` – форма изменения данных сервиса
  (view-функция `service_edit()`);
* `/services/<str:slug>/delete/` – подтверждение и удаление
  сервиса (view-функция `service_delete()`);
* `/services/<str:slug>/` – страница сервиса: карточка
  с данными, проверка доступности, история проверок из базы
  и кнопки CRUD (view-функция `service_detail()`);
* `/groups/` – список групп с числом сервисов в каждой
  (view-функция `groups()`);
* `/groups/<str:group_slug>/` – страница группы: описание,
  сервисы группы и статистика проверок
  (view-функция `group_detail()`).

Страницы формируются Django-шаблонами: view-функция
подготавливает контекст и вызывает `render(request, "…html", context)`.
Данные поступают из базы данных SQLite: представления выполняют
SQL-запросы через модуль `sqlite3`, получают строки
`sqlite3.Row` и передают их в шаблоны. HTML в Python-коде
представлений не собирается, функция `page()` удалена. Список
сервисов дополнительно отдаётся с заголовком
`Cache-Control: no-store`: браузер не показывает устаревшую
копию, данные перечитываются при каждом открытии.
Кнопки «Проверить» и «Проверить все сервисы» отправляют запросы
всем адресам одновременно: по мере ответов статус-бейдж
обновляется на месте, рядом с сервисом появляется плашка
«обновлено» и исчезает через две секунды. Без JavaScript работает
запасной вариант с редиректом на обновлённый список.

Идентификатор сервиса в URL совпадает с именем его JSON-файла
без расширения (`/services/youtube/`), идентификатор группы
получается из названия нижним регистром с подчёркиваниями
(`/groups/соцсети_и_мессенджеры/`). Если сервис или группа
с указанным идентификатором не найдены, представление передаёт
в шаблон пустое значение, страница показывает сообщение
об отсутствии объекта, а ответ получает код статуса 404.

Для адресов, которым не нашлось ни одного маршрута, работает
собственная страница ошибки: в корневом `servicemonitor/urls.py`
объявлен обработчик `handler404 = "homepage.views.page_not_found"`,
а сама view-функция `page_not_found()` возвращает шаблон
`homepage/404.html` со статусом 404. Обработчик действует для
всех приложений сразу и виден при `DEBUG = False` (при отладке
Django показывает техническую страницу). В файле `settings.py`
для работы при выключенной отладке заполнен `ALLOWED_HOSTS`,
а параметры локализации заданы как `LANGUAGE_CODE = "ru-RU"`
и `TIME_ZONE = "Europe/Moscow"`.

## Шаблоны Django (ПР6)

Веб-интерфейс построен на Django Template Language по схеме
**view → контекст → шаблон → HTML**.

* **Базовый шаблон** `templates/base.html` – общая структура
  страницы: `head`, кодировка, `viewport`, подключение Bootstrap
  и собственного CSS, логотип, навигация, основной контейнер,
  подвал и подключение JavaScript. Дочерние шаблоны
  переопределяют блоки `{% block title %}` и
  `{% block content %}`.
* **Наследование** – каждая страница начинается с
  `{% extends "base.html" %}` и заполняет блоки; общий HTML
  в дочерних шаблонах не дублируется.
* **Включаемые шаблоны** (`{% include %}`) – повторяющиеся
  фрагменты вынесены в отдельные файлы: навигация
  `templates/includes/navigation.html`, карточка сервиса
  `services/includes/service_card.html`, статус проверки
  `services/includes/service_status.html`. Карточка и статус
  повторно используются и в списке сервисов, и на странице группы.
* **Контекст** – представления передают данные в шаблон словарём:
  `{"services": services_list}`, `{"group": group, ...}`.
* **Циклы и условия** – `{% for %}…{% empty %}` для коллекций,
  `{% if %} / {% elif %} / {% else %}` для отображения статуса,
  наличия объекта и пустых значений.
* **Пространства имён и именованные URL** – в файлах `urls.py`
  приложений задан `app_name` (`homepage`, `services`, `groups`),
  ссылки в шаблонах формируются тегом `{% url %}` (например,
  `{% url 'services:detail' service.slug %}`), жёсткие адреса
  не используются.
* **Фильтры шаблонов** – `{{ services|length }}` (количество),
  `{{ service.name|default:"Без названия" }}` и
  `{{ code|default_if_none:"—" }}` (значение по умолчанию).
  Фильтры только форматируют вывод и не содержат бизнес-логику.
* **Статические файлы** – собственные CSS, изображение и
  JavaScript подключаются через `{% load static %}` и
  `{% static %}` (см. раздел «Статические файлы»).

## Статические файлы

Статические ресурсы приложения `homepage` расположены в
`homepage/static/homepage/`:

* `css/style.css` – собственное оформление: логотип, карточки
  сервисов и групп, статусы проверок, плашка «обновлено»;
* `js/main.js` – вывод текущего года в подвал и проверка сервисов
  в реальном времени;
* `img/logo.png` – логотип проекта.

В шаблоне `base.html` используется `{% load static %}`, а файлы
подключаются тегами `{% static 'homepage/css/style.css' %}`,
`{% static 'homepage/img/logo.png' %}` и
`{% static 'homepage/js/main.js' %}`. Bootstrap 5.3 подключается
через CDN и отвечает за базовую сетку и компоненты, а собственный
CSS оформляет элементы проекта.

## Основные операции

### Используется в веб-интерфейсе (ПР5 – ПР7)

* просмотр списка сервисов из базы данных;
* просмотр информации о сервисе и истории его проверок;
* просмотр списка групп;
* просмотр информации о группе и её сервисах;
* поиск сервисов по части названия и по группе;
* просмотр истории проверок с фильтром по статусу;
* просмотр статистики проверок (агрегаты, GROUP BY, HAVING);
* добавление, изменение и удаление сервисов;
* проверка всех сервисов одной кнопкой в реальном времени;
* проверка отдельного сервиса кнопкой из списка или со
  страницы самого сервиса;
* запись результатов проверок в базу данных.

### Отложено до следующих работ

* перенос сущностей `Group`, `Service`, `CheckResult`
  в Django ORM (ПР8 и далее);
* консольный поиск и сортировка остаются в версии ПР3.

## Хранение данных

Данные приложения хранятся в JSON-файлах:

* `data/groups.json` – группы сервисов;
* `data/<имя_сервиса>.json` – по одному файлу на каждый сервис.

При загрузке данные из JSON преобразуются в объекты `Group`
и `Service`. При сохранении объекты преобразуются в данные JSON.
Для связи сервиса с группой в его файле используется название
группы `group`.

Имя JSON-файла всегда совпадает с именем сервиса в нижнем
регистре с подчёркиваниями вместо пробелов — по нему строится
идентификатор сервиса в URL.

Группа «Тестовые сервисы» содержит сайты с нестандартным
поведением для наблюдения за реакцией мониторинга:

* `dns-отказ` – домен `.invalid` (IANA): отказ за 0.02 с;
* `ssl-ошибка` – просроченный сертификат: TLS-отказ за 0.5 с;
* `http_503` – httpbin.org отвечает 503 сразу, без таймаута;
* `медленный_ответ` – ответ приходит через ~5–6 секунд;
* `чёрная_дыра` – TEST-NET-1 (RFC 5737): висит ровно
  до таймаута 10 секунд;
* `google_generate_204` – спец-эндпоинт Google для проверки
  соединения: отвечает 204 за 0.2 с.

## База данных SQLite (ПР7)

На ПР7 данные проекта перенесены из JSON в реляционную базу
данных SQLite: `data/servicemonitor.sqlite`. JSON-файлы остаются
в проекте как исходные данные, перенесённые в базу.

### Структура базы данных

Таблица `groups` – группы сервисов:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | INTEGER | идентификатор, первичный ключ |
| `name` | TEXT | название группы (уникальное) |
| `slug` | TEXT | идентификатор для URL (уникальный) |
| `description` | TEXT | описание группы |

Таблица `services` – сервисы (основная сущность):

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | INTEGER | идентификатор, первичный ключ |
| `name` | TEXT | название сервиса (уникальное) |
| `slug` | TEXT | идентификатор для URL (уникальный) |
| `url` | TEXT | адрес проверки |
| `description` | TEXT | описание сервиса |
| `group_id` | INTEGER | ссылка на `groups.id` |

Таблица `checks` – результаты проверок сервисов:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | INTEGER | идентификатор, первичный ключ |
| `service_id` | INTEGER | ссылка на `services.id` |
| `available` | INTEGER | признак доступности (1/0) |
| `code` | INTEGER | код ответа (0 – нет ответа) |
| `checked_at` | TEXT | дата и время проверки |

Первичные ключи – поля `id` каждой таблицы. Внешние ключи:

* `services.group_id` → `groups.id` (группа содержит сервисы);
* `checks.service_id` → `services.id` (сервис содержит проверки).

Схема создаётся файлом `sql/schema.sql` (команды `CREATE TABLE
IF NOT EXISTS` с ограничениями `PRIMARY KEY`, `FOREIGN KEY`,
`NOT NULL`, `UNIQUE`, `DEFAULT`).

### Файлы работы с базой данных

* `data/servicemonitor.sqlite` – файл базы данных SQLite;
* `sql/schema.sql` – SQL-команды создания таблиц;
* `sql/queries.sql` – проверенные SQL-запросы проекта;
* `db/database.py` – подключение Python к базе
  (`get_connection()`, `sqlite3.Row`, `PRAGMA foreign_keys = ON`);
* `db/import_json.py` – перенос данных из JSON в таблицы
  (`executemany`, параметры `?`, `commit()`/`rollback()`);
* `data/checks.json` – пример истории проверок для импорта.

### SQL-запросы проекта

В `sql/queries.sql` собрано 15 запросов (с комментариями):

* выборка списков – запросы 1, 2, 3;
* фильтрация `WHERE` – запросы 4, 5, 6;
* соединение таблиц `JOIN` – запросы 7, 8;
* агрегатные функции (`COUNT`, `SUM`, `MAX`) – запросы 9, 10, 11;
* группировка `GROUP BY` – запросы 12, 13;
* фильтрация групп `HAVING` – запросы 14, 15.

### Получение данных в Django

Django-представления подключаются к базе через
`db.database.get_connection()`, выполняют параметризованный
SQL-запрос и передают результат (`sqlite3.Row`) в шаблон:
страницы списка сервисов, поиска, статистики и истории
проверок читают данные из SQLite. Проверки сервисов
записываются в таблицу `checks`.

## Назначение модулей

### `main.py`

Консольная версия приложения (сохранена с ПР3).
Отвечает за:

* запуск консольного приложения;
* отображение меню;
* получение данных от пользователя;
* организацию пользовательских сценариев.

### `servicemonitor/`

Пакет настроек Django-проекта:

* `settings.py` – настройки проекта (подключены приложения
  `homepage`, `services`, `groups`);
* `urls.py` – маршрутизация верхнего уровня;
* `asgi.py`, `wsgi.py` – точки взаимодействия с сервером.

### `templates/`

Каталог шаблонов уровня проекта (подключён в `settings.py`
параметром `DIRS`):

* `base.html` – базовый шаблон со структурой страницы,
  блоками `title` и `content`, логотипом, подвалом;
* `includes/navigation.html` – общая навигация сайта
  (ссылки через `{% url %}`).

### `homepage/`

Django-приложение, отвечающее за главную страницу:

* `views.py` – view-функция `index()` (главная страница)
  и обработчик `page_not_found()` (собственная страница 404);
  страницы формируются функцией `render()` и шаблонами;
* `urls.py` – маршрут главной страницы (`app_name = "homepage"`);
* `templates/homepage/index.html`, `templates/homepage/404.html` –
  шаблоны главной страницы и ошибки 404;
* `static/homepage/` – собственные CSS, JavaScript и логотип.

### `services/`

Django-приложение, отвечающее за сервисы:

* `views.py` – view-функции `services()` и `service_detail()`,
  `service_search()` (поиск), `service_statistics()`
  (статистика), `service_checks()` (история проверок),
  CRUD-функции (`service_create()`, `service_edit()`,
  `service_delete()`), проверки (`check_all()`,
  `service_check()`); представления получают данные из SQLite
  запросами SQL, готовят контекст, HTML формируют шаблоны,
  для JavaScript возвращаются JSON-ответы;
* `urls.py` – маршруты приложения (`app_name = "services"`);
* `templates/services/` – список, карточка, форма, подтверждение
  удаления и включаемые шаблоны карточки и статуса сервиса;
* `models.py` – Django-модели (заполняется в следующих работах).

### `groups/`

Django-приложение, отвечающее за группы сервисов:

* `views.py` – view-функции `groups()` и `group_detail()`;
* `urls.py` – маршруты приложения (`app_name = "groups"`);
* `templates/groups/` – список групп и карточка группы;
* `models.py` – Django-модели (заполняется в следующих работах).

### `group.py`, `service.py`, `check_result.py`, `monitor.py`

Классы предметной области (пакет ПР3):

* `group.py` – класс `Group` и связи с сервисами;
* `service.py` – класс `Service`, проверка доступности;
* `check_result.py` – класс `CheckResult` – результат проверки;
* `monitor.py` – класс `Monitor` – система, целостность связей
  и параллельная проверка всех сервисов с выводом результатов
  по мере поступления ответов.

### `checker.py`

Чистые функции-запросы над коллекциями:

* `service_slug()`, `group_slug()` – идентификаторы для URL;
* `find_service_by_slug()`, `find_group_by_slug()` – поиск
  объектов по идентификатору; используется веб-страницами
  сервиса и группы;
* `search_services()`, `sort_services()` – поиск и сортировка;
* `collect_results()`, `count_available()`,
  `percent_available()` – сбор и подсчёт результатов проверок
  (используется страницей группы).

### `storage.py`

Отвечает за загрузку и сохранение данных. Выполняет
преобразование:

* JSON → объекты Python;
* объекты Python → JSON.

### `db/`

Пакет работы с базой данных SQLite:

* `database.py` – функция `get_connection()`: соединение с
  `data/servicemonitor.sqlite`, `row_factory = sqlite3.Row`,
  включение проверки внешних ключей (`PRAGMA foreign_keys = ON`);
* `import_json.py` – перенос данных из JSON-файлов в таблицы
  (`INSERT` с параметрами `?`, `executemany`, транзакция
  `commit()`/`rollback()`).

### `sql/`

Каталог SQL-файлов:

* `schema.sql` – команды создания таблиц `groups`, `services`
  и `checks` с ключами и ограничениями;
* `queries.sql` – проверенные SQL-запросы проекта
  (списки, `WHERE`, `JOIN`, агрегаты, `GROUP BY`, `HAVING`).

### `utils.py`

Содержит вспомогательные функции консольного ввода:

* `input_int()` – безопасный ввод целого числа;
* `input_str()` – безопасный ввод непустой строки.

### `tests/`

Содержит автоматизированные тесты проекта.

## Запуск приложения

Установка зависимостей:

```text
pip install -r requirements.txt
```

Веб-версия (Django):

```text
python manage.py migrate
python manage.py runserver
```

Создание базы данных и перенос данных из JSON (ПР7):

```text
python -m db.import_json
```

Команда создаёт `data/servicemonitor.sqlite`, выполняет
`sql/schema.sql` и переносит группы, сервисы и историю проверок
из JSON-файлов. Файл базы данных уже находится в проекте,
повторный запуск пересобирает данные.

После запуска открыть в браузере адрес:

```text
http://127.0.0.1:8000/
```

Консольная версия (сохранена):

```text
python main.py
```

```text

```

## Текущее состояние и план развития

Реализовано (ПР5 – ПР7):

* Django-проект и три Django-приложения (`homepage`, `services`,
  `groups`);
* маршрутизация URL двух уровней, именованные маршруты
  и пространства имён (`app_name`);
* view-функции и страницы;
* отображение данных предметной области (сервисы и группы);
* проверка доступности сервиса через логику ПР3;
* CRUD-операции над сервисами (HTML-формы с CSRF-защитой);
* параллельная проверка всех сервисов: в консоли через
  `ThreadPoolExecutor`, в браузере через JavaScript
  с плашкой «обновлено»;
* навигация между страницами;
* оформление Bootstrap 5.3;
* система шаблонов Django: базовый шаблон `base.html`,
  наследование (`extends`, `block`), включаемые шаблоны
  (`include`), передача данных через контекст, циклы и условия,
  фильтры шаблонов;
* собственные статические файлы проекта: CSS, изображение
  (логотип), JavaScript;
* отказ от формирования HTML в Python-коде (функция `page()`
  удалена, страницы собирает `render()` с шаблонами);
* база данных SQLite (`data/servicemonitor.sqlite`) с таблицами
  `groups`, `services`, `checks` и внешними ключами;
* файлы `sql/schema.sql` и `sql/queries.sql` (15 запросов:
  списки, `WHERE`, `JOIN`, агрегаты, `GROUP BY`, `HAVING`);
* модули `db/database.py` (подключение, `sqlite3.Row`,
  `PRAGMA foreign_keys = ON`) и `db/import_json.py` (перенос
  данных из JSON, параметры `?`, `executemany`);
* получение данных из SQLite в Django-представлениях:
  страницы списка, поиска, статистики и истории проверок.

Планируется:

* перенос сущностей `Group`, `Service` и `CheckResult` в Django ORM;
* Django-формы (`forms.py`) вместо ручной обработки запросов;
* разработка API;
* контейнеризация приложения;
* настройка CI/CD.
